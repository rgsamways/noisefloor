## Context

See proposal.md for motivation and scope. This change consumes `@noisefloor/console-schema`'s `RadioLinkTelemetry` and `LinkProfile` types (implemented, archived 2026-09-21) and produces values of that shape. `packages/shared/src/gen` (parked case-study package) already solved an adjacent problem — deterministic, believable-looking generated series, via a tiny seeded PRNG (`rng.ts`, mulberry32) and per-shape generator functions (`foliage-year.ts` for seasonal/gradual, `shaper-collapse.ts` for sudden-step) — cited here as algorithmic precedent only; this change does not import from or depend on that package.

## Goals / Non-Goals

**Goals:**
- One small internal model that makes signal, SNR, rate, and retries move together, rather than 21 independently-jittered fields (handoff §6.1).
- A pure, deterministic function of (link profile, scenario, point in time) → `RadioLinkTelemetry` — same inputs always produce the same output, matching this repo's existing generator convention (`packages/shared/src/gen`'s functions are all pure, seeded, no internal mutable state) rather than a stateful simulation loop.
- Two fault shapes (sudden-step, gradual-ramp-recover) implemented generically enough that the three deferred radio-link faults (interference, cable degradation, foliage growth) and all five service-layer faults can plausibly reuse them later, per proposal.md's explicit deferral list.

**Non-Goals:**
- No real RF propagation physics (Friis equation, fade margin calculations, etc.). "A small physics model with a few knobs" (handoff §6.1) is read as *physics-flavored*, not *physically rigorous* — the goal is a panel that reads as real to a trained tech, not a link-budget calculator.
- No console UI, no persistence, no streaming/websocket delivery — this change is a function callers can call, not a running service.
- No service-layer faults, no log simulation, no interference/cable/foliage time-signatures — deferred per proposal.md, though the mechanism built here is meant to carry them.
- No derived-value logic changes to `console-schema` itself (e.g. how SNR-from-noise-floor derivation works when a vendor doesn't report it) — that Non-Goal from `radio-console-schema`'s own design.md still holds; this engine computes SNR directly as part of its internal model, it doesn't derive it from a separately-generated noise floor.

## Decisions

**A single internal `linkHealth` scalar (0–1) per side, mapped to the visible fields, rather than modeling each field independently.** This is the concrete answer to "a small physics model with a few knobs": one number represents "how good is this link right now," and `signalDbm`, `snrDb`, `modulationIndex`, `txRateMbps`/`rxRateMbps`, and `errorsRetries` are each a deterministic (possibly per-`LinkProfile`) function of that scalar plus a small amount of seeded jitter. This is what makes correlated movement automatic rather than something each fault has to remember to do to every field it touches — a fault only ever modifies `linkHealth` (directly, or through a time-signature shape), and every dependent field moves together because they all read from it.

**Alternative considered:** hand-write per-field correlation rules (e.g. "when signal drops by X, drop SNR by Y and step rate down by one MCS level per Z dB"). Rejected as the default approach because it multiplies the amount of fault-specific logic every new fault has to get right — exactly the kind of one-off branching proposal.md's extensibility requirement is trying to avoid — though nothing prevents a future fault from having a field-specific rule layered on top of the shared scalar if one is ever needed.

**Healthy-baseline target is a function of `LinkProfile`, not a constant.** `distanceKm`, `band`, and `gearClass` feed a simple, explicitly-approximate mapping to a baseline `linkHealth` and a baseline `signalDbm` range (e.g., a longer distance or a lower-tier `gearClass` implies a lower baseline signal, without modeling actual path loss) — enough to satisfy the spec's "two profiles produce different healthy baselines" requirement without pretending to be a propagation model.

**Faults are `{ shape: "step" | "rampRecover"; startAt; ...shape-specific params }` applied as a modifier to `linkHealth` over simulated time, not a per-fault case statement.** `"step"` applies an instantaneous, persistent delta at `startAt`. **Wind misalignment is this shape's driving parameterization, and it manifests specifically through `chainImbalanceDb`** — confirmed against real field experience: alignment problems are obvious once chain delta reaches roughly 5 dB or more, and it stays that way rather than self-correcting. The step therefore targets `chainImbalanceDb` directly (with the scalar-derived fields moving in sympathy through the normal `linkHealth` mapping), not a generic "signal got worse" delta. `"rampRecover"` applies a delta that ramps in over a configured duration and ramps back out over a second configured duration — **both fully caller-configurable, not fixed to any particular timescale.** Rain fade is this shape's driving parameterization; real rain fade duration tracks how long the rain lasts, which can run from minutes to multiple hours, so the shape's parameters must support the long end of that range as a normal case, not an edge case. A future fault (interference, foliage growth, etc.) is expected to be a new named parameterization of one of these two shapes, or — if genuinely neither fits (e.g. interference's daily-rhythm intermittency) — a third shape added to the same mechanism, not a special case bolted onto the engine's core loop.

**Staleness is handled by freezing `linkHealth`'s evolution for the affected side and repeating its last computed `Reading`, not by a separate "stale mode" branch in every field mapping.** When a scenario simulates a far-end drop, the engine stops advancing that side's `linkHealth` (and therefore every field derived from it) and returns the same `{ value, asOf }` pairs it last computed, satisfying the spec's "value stops changing, asOf stays fixed" requirement without needing per-field staleness logic.

**Package: new `packages/simulation-engine`, depending on `@noisefloor/console-schema`.** Not folded into `console-schema` itself — that package is intentionally shape-only per its own design.md ("no derived-value logic... schema package has no behavior, only shape and Zod validation"), and this engine is nothing *but* behavior.

## Risks / Trade-offs

- **[Risk, confirmed] A single scalar per side is too coarse to express "good signal, bad airtime" — and this is a real gap, not just a hypothetical one.** Confirmed on review: this second axis (a separate "capacity health" scalar for airtime/utilization/client-count, decoupled from the signal-chain scalar this change builds) **will be needed later**, not just might be. → **Mitigation**: explicitly out of scope for this change by design — it's deferred to a follow-up change once the interference/cable/foliage fault work makes the need concrete, rather than guessed at speculatively here. Not a reason to hold up this change, but should be treated as a near-term commitment, not a maybe, when scoping what comes after it.
- **[Risk] The healthy-baseline-by-LinkProfile mapping is invented, not derived from real field data or Robin's on-the-job experience.** → **Mitigation**: same posture as `radio-console-schema`'s own schema-accuracy risk — flagged for review before implementation is authorized, expected to need correction from someone who's actually looked at a 15 km link's real numbers versus a 200 m one.
- **[Risk] Pure-function-of-time design means a caller wanting a "live" feed must repeatedly call with an advancing timestamp, rather than subscribing to a stream.** → **Mitigation**: acceptable for this change (no UI consumer yet); revisit only when a console UI change actually needs a delivery mechanism, not before.
